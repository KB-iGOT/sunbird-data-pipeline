## 1. Executive Summary

The Sunbird Analytics Data Pipeline is a distributed, real-time stream processing system that ingests telemetry events generated by Sunbird platform clients (mobile apps, web portals, desktop apps) and transforms them into queryable analytical data in Apache Druid. The pipeline is built on Apache Flink for stateful stream processing, Apache Kafka for durable event transport, Redis for low-latency cache and deduplication, and Apache Cassandra for reference data. A Apache Spark batch layer handles periodic merge operations. The system is designed for high throughput (targeted at 100k+ TPS), at-least-once delivery guarantees, and horizontal scalability through configurable operator parallelism. The pipeline enforces schema validation, deduplication, event enrichment (device, user, content, location), and privacy redaction before events reach Druid for analytics consumption.

## 2. System Overview & Goals

### 2.1 Problem Statement

Sunbird platform clients emit structured telemetry events (interactions, assessments, impressions, errors, shares, and audit events) that must be ingested at scale, validated, enriched with reference data, deduplicated, and made available for near-real-time and batch analytics.

### 2.2 Design Goals

| Goal | Mechanism |
|---|---|
| High throughput (100k+ TPS) | Flink operator parallelism, Kafka partitioning, tunable batch/linger on producers |
| Exactly-once deduplication | Redis-backed `DedupEngine` with configurable TTL per pipeline stage |
| Schema correctness | JSON Schema validation against versioned envelope schemas |
| Data enrichment | Redis DataCache lookups for device, user, content, location, dial-code data |
| Privacy compliance | PII redaction of user responses for Registration-type assessment questions |
| Fault tolerance | Flink checkpointing to `FsStateBackend` (blob/GCS/S3/HDFS), fixed-delay restart strategy |
| Observability | Per-operator Flink Gauge metrics registered under job name metric group, Kafka dead-letter topics |
| Long-term archival | Secor (Kafka-to-blob archival), Azure Blob Storage |

### 2.3 Out of Scope

- Client-side telemetry SDK
- Druid query layer and visualization (Superset/Metabase)
- API gateway and authentication

## 6. Data Flow — End to End

### Step 1 — Client Emission
Mobile/web/desktop clients batch telemetry events into JSON envelopes (containing an `events` array, `params.msgid`, `params.did`, `params.channel`, etc.) and POST them to the Telemetry API over HTTPS.

### Step 2 — Ingest Routing
The **IngestRouter** Flink job fans in events from multiple ingest sources (different API endpoints, SDK versions, channels) and publishes normalized batch strings to `kafka.input.topic`.

### Step 3 — Telemetry Extraction (`TelemetryExtractorStreamTask`)

**3a. Batch Deduplication** — `DeduplicationFunction` reads the raw String batch from `kafka.input.topic`, extracts `params.msgid` via `JSONUtil.deserialize`, and calls `DedupEngine.isUniqueEvent(msgid)` against Redis DB `redis.database.duplicationstore.id`. Unique batches are deserialized to `Map[String,AnyRef]` and emitted to `uniqueEventOutputTag`. Duplicate batches go to `kafkaDuplicateTopic`. Unparseable batches go to `kafkaBatchFailedTopic`.

**3b. Event Extraction** — `ExtractionFunction` receives the unique batch map, reads `events` array, stamps each event with `syncts` (ISO-8601 UTC from batch `syncts` field or `System.currentTimeMillis()`) and `@timestamp`. Each event is serialized to JSON and size-checked against `kafka.event.max.size`. Oversized events are flagged (`flags.ex_processed=false`, `metadata.ex_error='Event size is Exceeded'`) and routed to `kafkaFailedTopic`. Events with `eid` in `redact.events.list` (e.g., ASSESS, RESPONSE) go to `assessRedactEventsOutputTag`. `LOG` events go to `kafkaLogRouteTopic`. All others go to `kafkaSuccessTopic` (raw). One synthetic audit `LOG` event per batch is generated and emitted to `kafkaLogRouteTopic`.

**3c. PII Redaction** — `RedactorFunction` receives events from `assessRedactEventsOutputTag`, extracts the question ID (`edata.item.id` for ASSESS, `edata.target.id` for RESPONSE), and calls `DataCache.getWithRetry(questionId)` on Redis DB `redis-meta.database.contentstore.id` using `metaRedisHost:metaRedisPort`. If `questionType == "Registration"` (case-insensitive), the original unredacted event is cloned to `kafkaAssessRawTopic`, then `edata.resvalues` (for ASSESS) or `edata.values` (for RESPONSE) is cleared to an empty `ArrayList` before routing to `kafkaSuccessTopic`.

### Step 4 — Pipeline Preprocessing (`PipelinePreprocessorStreamTask`)

**4a. Schema Validation** — `TelemetryValidator` (called within `PipelinePreprocessorFunction.processElement`) validates each `Event` against JSON schemas loaded from classpath path `telemetry.schema.path`, starting with `envelope.json`. Events failing validation are flagged (`pp_validation_processed=false`) and routed to `kafkaFailedTopic`.

**4b. Log Routing** — Valid `LOG` events are immediately routed to `kafkaLogRouteTopic` and bypass deduplication.

**4c. Event-Level Deduplication** — All non-LOG valid events are checked against `DedupEngine` using `event.mid()` as the key, against Redis DB `redis.database.duplicationstore.id`. Duplicates are flagged (`pp_duplicate=true`) and routed to `kafkaDuplicateTopic`.

**4d. Hub Field Enrichment** — For `IMPRESSION`, `INTERACT`, `START`, `END` events, `event.env` is mapped to a hub category (learn, discuss, network, careers, competency, events, other) and written back to the event via `event.updateHub(hub)`.

**4e. Event Routing** — Unique events are pattern-matched by `eid`:
- `AUDIT` → `kafkaAuditRouteTopic` + `kafkaPrimaryRouteTopic`
- `SHARE` → `ShareEventsFlattener.flatten()` generates `SHARE_ITEM` child events to `kafkaPrimaryRouteTopic`; original SHARE also to `kafkaPrimaryRouteTopic`
- `ERROR` → `kafkaErrorRouteTopic` + denorm routing
- `CB_AUDIT` → `kafkaCbAuditRouteTopic`
- Secondary eids (from `secondary.events` config list) → `kafkaDenormSecondaryRouteTopic`
- All others → `kafkaDenormPrimaryRouteTopic` + `kafkaPrimaryRouteTopic`

### Step 5 — Telemetry Merger (Spark)

The **TelemetryMerger** Spark job consumes from `kafkaDenormPrimaryRouteTopic` and `kafkaDenormSecondaryRouteTopic` in batch windows and merges/compacts the event streams into a unified `sink-topic`, handling any ordering or window semantics required before enrichment.

### Step 6 — Telemetry Denormalization (`TelemetryDenorm`)

**TelemetryDenorm** enriches each event from `sink-topic` with:
- **Device data** — Redis lookup by `did`; populated fields written to `devicedata` path
- **User data** — Redis lookup by `uid/actor.id`; fields written to `userdata` path
- **Content data** — Redis lookup by `object.id`; fields written to `contentdata` path
- **Dial-code data** — Redis lookup + optional `RestUtil.get()` call; written to `dialcodedata` path
- **Collection data** — Redis lookup; written to `collectiondata` path
- **Derived location** — IP/device-based geo; written to `derivedlocationdata` path
- **L2 data** — Written to `l2data` path

Enriched events are emitted to `denorm-topic`.

### Step 7 — Druid Validation and Routing

**DruidEventsValidator** performs final structural/type validation of enriched events from `denorm-topic`. Valid events proceed to `DruidRouter`, which routes events to:
- Druid Summary cluster topics (aggregated metrics)
- Druid Raw cluster topics (full event detail)
- Failed topic (events that cannot be ingested)

### Step 8 — Side Pipeline Processing (concurrent with Steps 3–7)

- **UserCacheUpdater** — Consumes `log-route-topic`; upserts user profile data into Redis user DB
- **DeviceProfileUpdater** — Consumes `denorm-topic`; maintains device metadata in Redis device DB and Cassandra
- **ContentCacheUpdater** — Consumes raw events; refreshes content metadata in Redis content DB from Cassandra content hierarchy
- **AssessmentAggregator** — Consumes raw ASSESS events; computes and persists aggregated scores to Cassandra
- **CBPreprocessor** — Consumes raw events; processes competency-based events and routes to `cb-audit-route-topic`

### Step 9 — Archival

Secor continuously tails all major Kafka topics and writes Avro/JSON files to Azure Blob Storage, organized by topic, date, and hour, providing long-term retention independent of Kafka log retention.

### Redis Connectivity Model

Each Flink operator that uses Redis holds a single `RedisConnect` instance created in `open(Configuration)` and closed in `close()`. `RedisConnect` creates a fresh `Jedis` socket per `getConnection()` call — there is no connection pool. `DataCache` and `DedupEngine` each hold one live `Jedis` handle internally. On `JedisException`, both classes close the current connection, sleep 10,000 ms (`DedupEngine`) or reconnect immediately (`DataCache`), and retry once.

Two Redis instances are used:
- **Primary Redis** (`redisHost:redisPort`, default `localhost:6379`) — dedup store, user/device caches
- **Meta Redis** (`metaRedisHost:metaRedisPort`) — content store (question metadata, content metadata)

## 9. External Dependencies

### 9.1 Apache Cassandra

| Use Case | Access Pattern | Consistency | Job |
|---|---|---|---|
| User metadata lookup | `findOne` by user ID | QUORUM | `TelemetryDenorm`, `UserCacheUpdater` |
| Content hierarchy | `find` by content ID | QUORUM | `ContentCacheUpdater` |
| Assessment aggregation | `upsert` (INSERT with LWT `wasApplied`) | QUORUM | `AssessmentAggregator` |
| Device profile persistence | `upsert` | QUORUM | `DeviceProfileUpdater` |

`CassandraUtil` connects to a single contact point. QUORUM consistency is set globally. The `find()` method catches `DriverException` and rethrows — callers handle reconnection manually via `reconnect()`.

### 9.2 PostgreSQL

Used by jobs requiring org/user reference data not available in Redis or Cassandra. `PostgresConnect` uses `PGPoolingDataSource` (deprecated) with `maxConnections` limiting concurrency. `execute()` auto-retries once on `SQLException` via `resetConnection`. `executeQuery()` has no retry. The `PostgresConnectionConfig` case class carries `host`, `port`, `user`, `password`, `database`, `maxConnections`.

### 9.3 External REST APIs

`RestUtil` provides a stateless Apache HttpClient GET method used primarily by dial-code lookup flows (`ContentCacheUpdater` / `TelemetryDenorm`). A new `HttpClient` is instantiated per request. No retry, no timeout configuration, no connection pooling. The `DialCodeResult` case class is defined in `RestUtil.scala` for callers to use when parsing responses via Gson.

## 10. Scaling & Parallelism Strategy

### 10.1 Parallelism Configuration

All jobs derive operator parallelism from `BaseJobConfig`:

| Config Key | Purpose | Default Scope |
|---|---|---|
| `task.consumer.parallelism` | Kafka source operator parallelism | Per-job, matches Kafka topic partition count |
| `task.downstream.operators.parallelism` | Processing operator parallelism | Per-job, typically 2–4x consumer parallelism |
| `parallelism` (base) | Default operator parallelism | Applied to operators not explicitly set |

`TelemetryExtractorStreamTask` applies `kafkaConsumerParallelism` to the source and `downstreamOperatorsParallelism` to `DeduplicationFunction`, `ExtractionFunction`, and `RedactorFunction`. `PipelinePreprocessorStreamTask` applies the same pattern to `PipelinePreprocessorFunction`.

### 10.2 Kafka Producer Tuning

`BaseJobConfig.kafkaProducerProperties()` exposes:
- `kafkaProducerLingerMs` — controls batching latency
- `kafkaProducerBatchSize` — controls batch size in bytes
- `kafkaProducerCompression` — defaults to `snappy` (reduces network bandwidth ~50%)
- `kafkaProducerMaxRequestSize` — caps individual request size

### 10.3 Scaling Constraints

- **Redis bottleneck** — `DedupEngine` and `DataCache` are single-connection per operator instance. At high parallelism, the number of live Redis sockets scales linearly with `downstreamOperatorsParallelism × number_of_task_managers`. No connection pooling mitigates this.
- **Kafka partition count** — `kafkaConsumerParallelism` must not exceed the number of partitions on `kafka.input.topic` or Flink will idle the extra consumer threads.
- **Flink rebalance** — `PipelinePreprocessorStreamTask` calls `.rebalance()` after the source to distribute events evenly across downstream parallel subtasks before they reach `PipelinePreprocessorFunction`.

## 11. Fault Tolerance & Checkpointing

### 11.1 Flink Checkpointing

Configured in `FlinkUtil.getExecutionContext()`:

| Parameter | Config Key | Description |
|---|---|---|
| Checkpoint interval | `checkpointing.interval` | Milliseconds between successive checkpoint triggers |
| Min pause between checkpoints | `checkpointing.pause.seconds` | Minimum gap (seconds) after a checkpoint completes before the next starts; prevents checkpoint storms |
| Compressed snapshots | `enable.compressed.checkpointing` | Enables Flink snapshot compression to reduce checkpoint size |
| State backend | `checkpointing.base.url` + `jobName` | `FsStateBackend` pointing to `<checkpointingBaseUrl>/<jobName>` when `enable.distributed.checkpointing=true` |
| Externalized checkpoints | `RETAIN_ON_CANCELLATION` | Checkpoints are not deleted on job cancellation; enables manual recovery |
| Time characteristic | `IngestionTime` | Event timestamps are assigned at Flink source ingestion, not at client emission |

### 11.2 Restart Strategy

All jobs use `RestartStrategies.fixedDelayRestart`:
- **Max attempts** — `restartAttempts` from `BaseJobConfig`
- **Delay between attempts** — `delayBetweenAttempts` milliseconds

### 11.3 Kafka Sink Semantics

All Kafka sinks use `Semantic.AT_LEAST_ONCE`. There is no two-phase commit / exactly-once producer. Deduplication at the next stage (`DedupEngine`) compensates for potential duplicates introduced by at-least-once delivery after Flink restarts.

### 11.4 Redis Fault Handling

- `DedupEngine` — On `JedisException`, closes connection, sleeps 10,000 ms, reconnects, retries. If retry fails, the exception propagates and triggers the Flink restart strategy.
- `DataCache` — On `JedisException`, immediately reconnects and retries once. No sleep.
- `CassandraUtil` — On `DriverException` in `find()`, logs and rethrows. No automatic reconnect; callers invoke `reconnect()` explicitly.
- `PostgresConnect` — `execute()` auto-retries via `resetConnection()` on `SQLException`. `executeQuery()` does not retry.

### 11.5 Dead-Letter Topics

Every pipeline stage routes malformed, oversized, validation-failed, and duplicate events to designated dead-letter topics (`kafka.output.failed.topic`, `kafka.output.batch.failed.topic`, `kafka.output.duplicate.topic`). These topics are consumed by Secor for archival and are available for manual inspection and selective reprocessing.

## 12. Backup & Archival

### 12.1 Secor (Kafka-to-Blob Archival)

Secor runs as a continuous Kafka consumer subscribing to all major topics. It writes partitioned files (organized by `topic/year/month/day/hour`) to Azure Blob Storage. This provides:
- Long-term retention beyond Kafka log retention limits
- Input source for ad-hoc reprocessing using Spark batch jobs
- Audit trail for compliance

### 12.2 Flink Checkpoint Storage

When `enable.distributed.checkpointing=true`, `FsStateBackend` writes checkpoint snapshots to `checkpointingBaseUrl/jobName` on Azure Blob Storage. Snapshots include:
- Kafka consumer offsets (per-partition committed positions)
- Flink operator keyed/managed state (if any stateful operators use Flink state primitives beyond in-process variables)
- `RETAIN_ON_CANCELLATION` ensures snapshots survive job cancellation for manual recovery

### 12.3 Checkpoint Recovery Procedure

On job failure exceeding `restartAttempts`, the job enters FAILED state. Recovery options:
1. **Automatic** — Within `restartAttempts`, Flink restores from the latest completed checkpoint and replays Kafka events from the checkpointed offsets
2. **Manual** — Submit the job with `--fromSavepoint <checkpointPath>` pointing to a retained checkpoint in Azure Blob Storage

### 12.4 Assess Raw Topic Archival

Pre-redaction copies of Registration-type assessment events are written to `kafka.output.assess.raw.topic` by `RedactorFunction`. This topic is separately archived by Secor with restricted access, providing the full unredacted event record for authorized research use while the main pipeline carries only the redacted version.
