Issues Being Fixed
Hop Waste
telemetry.raw round-trip
At 100k TPS the batch API produces ~10 events per batch. telemetry.raw carries ~1M events/sec — that's ~2M Kafka I/O ops/sec (producer + consumer) just to ferry events between two jobs that could be one job.
Hop Waste
telemetry.denorm round-trip
druid-events-validator reads ~100k events/sec from telemetry.denorm, does a dedup check that was already disabled (P1.5), then re-publishes to two topics. Pure overhead: ~200k Kafka ops/sec with no value added.
Blocking I/O
Synchronous Redis in de-normalization
Operator thread calls pipeline.sync() and blocks until all 4 Redis instances respond. At 64k TPS the thread spends ~95% of its time waiting on network I/O — not processing events.
Config Bug
Parallelism = 1 on all jobs
Single JVM thread per job regardless of available CPU. The HPA auto-scaling block was fully written in the deployment template but every line was commented out.
Code Bug
isDuplicateCheckRequired always true
Forced Redis dedup calls for mobile events that are structurally never duplicated. Wasted ~500k Redis ops/sec at peak. Only portal and desktop events need dedup.
Redundant
Double dedup at druid-validator
Events were already deduped in preprocessor (Redis DB2). druid-validator re-checked them in DB8. Added ~100k Redis ops/sec for zero benefit.
Unchanged New / Merged Modified Shadow write (30-day SECOR drain)

What Changed
P2.5
Telemetry Intake — merged job
Extractor + Preprocessor merged into TelemetryIntakeStreamTask. Eliminates telemetry.raw as a pipeline hop. HOCON namespacing (extractor{} / preprocessor{}) resolves config key conflicts. Saves ~2M Kafka I/O ops/sec at 100k TPS.
P3.1
Direct Druid routing from de-normalization
Two filter sinks added directly on the denorm stream to write to druid.events.telemetry and druid.events.summary. druid-events-validator job eliminated entirely. Saves ~200k Kafka ops/sec + one running Flink job.
P2.2
Async I/O in de-normalization (Lettuce)
Replaced blocking Jedis pipeline.sync() with async Lettuce futures. Operator thread issues all 6 Redis fetches concurrently and returns immediately to process the next event. Up to 500 events have in-flight Redis fetches simultaneously.
P2.3
Caffeine in-process cache (50k entries, 5-min TTL)
Popular device/user/content IDs served from local heap. 50–70% hit rate for active content IDs. Bypasses Redis entirely for those lookups — nanosecond vs millisecond latency.
P2.1
Bloom filter in DedupEngine
Guava BloomFilter (10M entries, 0.0001 FP rate, ~24MB) pre-checks before Redis EXISTS. Zero false negatives — definitely-unique events skip Redis. 60–80% fewer dedup Redis calls.
P1.1 · P1.2
Parallelism 1 → 4 + HPA enabled
Single biggest throughput gain overall. The entire HPA block was already written in the deployment template but commented out — uncommented it. Jobs now auto-scale under burst traffic.

Key Changes vs Optimized
Broker
Kafka 3.7 (KRaft) → Redpanda 24.x
C++ vs JVM: ~10× throughput per node (1.5–2 GB/s vs 300–500 MB/s). P99 latency 1–5ms vs 10–50ms. Built-in Schema Registry enforces Avro at produce time — Flink never sees a malformed event. Tiered storage to S3 replaces SECOR entirely.
Eliminated
Ingest Router — gone
Redpanda accepts direct SDK writes via the standard Kafka producer protocol. The pass-through relay job that provided the monitoring boundary is replaced by Redpanda's built-in consumer lag metrics per topic.
Processing
Flink 1.13 → Flink 2.0 (Java 17)
Adaptive batch scheduling (no manual parallelism tuning). Unified Table/SQL API for routing logic. Improved RocksDB state backend for larger Bloom filters. Dedup upgraded from Redis EXISTS to DragonflyDB SET NX (atomic, no race condition).
Eliminated
Redis → DragonflyDB
Same Lettuce client, zero code changes. DragonflyDB is multi-threaded: 25× more throughput per node than single-threaded Redis. At 1M TPS a single DragonflyDB node handles dedup comfortably. Eliminates Redis Cluster complexity.
Eliminated
Apache Druid → ClickHouse
Druid requires 6 JVM services minimum. ClickHouse ingests directly from Kafka (Kafka Engine table type) — no separate ingestion job. Query latency: 1–5s → <100ms. Materialized views update in real time. 60% lower infra cost at scale.
Topics
16 active topics → 6
telemetry.ingest · telemetry.processed · telemetry.audit · telemetry.dlq · druid.events.telemetry · druid.events.summary
All the intermediate routing topics (telemetry.unique.secondary, telemetry.error, telemetry.cb.audit, etc.) collapse into the single telemetry.processed topic with Flink SQL routing.
Archival
SECOR → Apache Iceberg on S3/GCS
Iceberg is written directly by EnrichmentJob as a second sink. Format: Parquet (5–10× smaller than SECOR JSON). ACID, schema evolution, time-travel. Query with Trino/Spark SQL — no need to load into Druid for historical analytics.

Processing Steps — per event
1
Age check. If event is older than ignorePeriodInMonths (default: 3 months) → skip entirely, increment eventsExpired counter. Prevents enriching and storing stale analytics data.

2
Event type filter. SUMMARY events (except ME_WORKFLOW_SUMMARY) and events in the skip list (LOG) are skipped. ME_WORKFLOW_SUMMARY is explicitly processed. All other SUMMARY variants are skipped.

Key events by did hash mod shards → count window. Events are grouped by device ID hash (1400 shards default, tuned to 400 in optimized). Window fires after N events per shard. This enables batch Redis lookups (pipeline) across a window of events sharing similar device IDs.

Critical Issues
